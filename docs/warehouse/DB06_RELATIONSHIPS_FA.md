# DB-06؛ مدل مشترک ارتباط‌ها و شواهد UTXO

این گزارش گام DB-06 است؛ ارتقای بعدی به نسخهٔ ۵ در [DB-07](DB07_VISIBILITY_FA.md)
انجام شده و تعریف تاریخی نسخهٔ ۴ دست‌نخورده باقی است.

این گام مدل `typed_relationships_v1` و reader محدود و مشترک گراف را برای چهار
شبکه تعریف می‌کند. writer و API بیت‌کوین آن را مصرف می‌کنند؛ پنل و تبدیل
snapshot در نود مرکزی نیز subjectهای نوع‌دار را حفظ می‌کنند. انتقال writer،
reader و تاریخچهٔ legacy سه شبکهٔ دیگر در DB-08 باقی است.

## ساختار دیتابیس و استقرار

قرارداد ذخیره همان نسخهٔ **۴** با **۳۸ جدول، ۴۰ view و ۶۶۸ ستون جدول** است.
ستون‌های موردنیاز subject، نوع، event/output index و outpoint از قبل وجود
داشتند؛ migration جدید یا بازنویسی نسخه‌های قبلی لازم نیست. checksum نسخهٔ ۴:

`955e0c5ff2e6bb7000793e66408312f4d0172d026f15f328a9431ee050b568ec`

نسخهٔ تفسیر رابطه از نسخهٔ schema جداست. این کنترل‌های سخت‌گیرانه در مرز
نوشتن/خواندن گراف اجرا می‌شوند و قواعد تاریخی نسخهٔ ۴ را عوض نمی‌کنند.
رکورد قدیمی ناسازگار پاک یا خودکار بازتفسیر نمی‌شود؛ تبدیل صریح آن DB-08 است.
ClickHouse، database و volume هر شبکه روی VM خودش مستقل می‌مانند.
`shared/warehouse` فقط کتابخانهٔ مشترک Rust و منبع قرارداد است.

## هویت گره و معنای یال

هر گره `network_id`، `subject_id` و `subject_type` دارد و کلید کامل آن شامل
هر سه است. `address` فقط برای گره آدرس مقدار دارد؛ در تراکنش و script برابر
NULL است. خوانندهٔ API و پنل از `subject_id` برای اتصال استفاده می‌کنند.

| شبکه / شواهد | جهت ارتباط | معنای مبلغ |
|---|---|---|
| TRON، Ethereum، BSC | address → address | انتقال مشاهده‌شده، با asset، مقدار صحیح دقیق و موقعیت رویداد اصلی |
| ورودی بیت‌کوین | address یا script → transaction | ارزش prevout مصرف‌شده؛ vin index و txid/vout قبلی حفظ می‌شوند |
| خروجی بیت‌کوین | transaction → address یا script | ارزش همان خروجی؛ vout index و outpoint جاری حفظ می‌شوند |

دو ورودی و سه خروجی، پنج leg مشاهده‌شده می‌سازند. هیچ حاصل‌ضرب شش‌تایی
یا فرستندهٔ واحد ساخته نمی‌شود. `ownership_claimed`،
`fund_continuity_claimed` و `amount_allocation_claimed` در خروجی false هستند.
Coinbase ورودی خرج‌شده ندارد؛ leg خروجی‌های آن حفظ می‌شود. script بی‌آدرس،
از جمله خروجی با مقدار صفر، به آدرس حدسی تبدیل نمی‌شود.

شناسهٔ تراکنش همان `tx:<block_hash>:<tx_hash>` قبلی است تا وقوع‌های تکراری
یک txid در دو بلاک یکی نشوند. هویت یال علاوه بر شبکه و شناسهٔ leg، hash،
commit و revision را دربر می‌گیرد. شناسهٔ script برای سازگاری با دادهٔ مستقر
همان `script:SHA256(canonical_hex_text)` قبلی است؛ این digest متن hex است و
نباید با hash بایت‌های script یا hash اجماعی P2WSH اشتباه شود. خود script در
fact اصلی حفظ می‌شود و در این گام شناسهٔ تاریخی تغییر نمی‌کند.

مدل مشترک آدرس‌های EVM را در مرز ورودی lowercase و آدرس TRON با قالب hex41
را به Base58Check تبدیل می‌کند؛ ردیف ذخیره‌شده باید از ابتدا canonical باشد.
برای Bitcoin، مدل مشترک فقط نحو و prefix mainnet را کنترل می‌کند. adapter
بیت‌کوین checksum و mainnet را بررسی و آدرس را از script واقعی استخراج می‌کند؛
writer اختلاف آدرس ادعاشده و script را پیش از درج رد می‌کند.

## خواندن قابل ممیزی

`relationships::read_neighborhood` تنها viewهای canonical را می‌خواند:

1. هویت database/شبکه، subject و حدها پیش از query بررسی می‌شوند.
2. وضعیت publication پیش از خواندن ثبت می‌شود.
3. وقوع تراکنش با tuple کامل height/hash/commit/revision/tx/index انتخاب
   می‌شود؛ انتخاب فقط با txid انجام نمی‌شود. زمینهٔ کامل روابط وقوع انتخاب‌شده
   تا سقف یال‌ها خوانده می‌شود، نه فقط یال متصل به آدرس جست‌وجوشده.
4. هر leg بیت‌کوین با fact canonical ورودی/خروجی بر اساس header کامل، زمان،
   موقعیت تراکنش، vin/vout index، مبلغ، subject، آدرس nullable و outpoint
   تطبیق می‌یابد. witness مفقود یا ناسازگار خطا می‌دهد و پنهان نمی‌شود.
5. انواع و مقادیر قرارداد و معنای رابطه اعتبارسنجی می‌شوند. سقف ۱۰۰ وقوع و
   ۲۰۰۰ یال است؛ عبور از حد با `truncated=true` مشخص می‌شود.
6. تغییر وضعیت publication در طول خواندن باعث خطای snapshot و نیاز به retry
   می‌شود. این کنترل، جایگزین قرارداد کامل invalidation در DB-07 نیست.

UInt256 و ساتوشی به‌صورت رشتهٔ صحیح دقیق به گراف می‌رسند. شمارهٔ ورودی با
`input_index` و شمارهٔ خروجی با `output_index` مشخص است. شناسهٔ leg، outpoint،
evidence refs و headerهای ممیزی حفظ می‌شوند؛ JSON خام تکراری در یال پنل
بازنشر نمی‌شود و در fact اصلی باقی می‌ماند.

منبع SQL در `shared/warehouse/src/relationships/query.sql` و نسخهٔ قابل بررسی
adapter در `dockerizd_bitcoin/sql/queries/relationships.sql` است. exporter و
تست داخلی اختلاف آن‌ها را رد می‌کنند. فایل query با placeholder مستقیماً
اجرا نمی‌شود؛ reader فقط شناسه‌های معتبر، literalهای escapeشده و حد عددی
را جایگزین می‌کند. این فایل DDL و migration پنجم نیست.

## API، پنل و نود مرکزی

investigation و جست‌وجوی مسیر بیت‌کوین از reader مشترک استفاده می‌کنند.
مسیرها شامل گره تراکنش‌اند، ترتیب `(height, transaction_index)` رو به جلو
دارند و فقط `possible_transaction_connectivity` گزارش می‌کنند. جست‌وجو
محدود است؛ پیدا نشدن مسیر، اثبات نبودن مسیر نیست و تخصیص ارزش ورودی به خروجی
یا مالکیت مشترک از آن نتیجه نمی‌شود.

پنل subjectهای تراکنش و script با آدرس NULL را نمایش می‌دهد و برای snapshotهای
قدیمی fallback دارد. تبدیل مرکزی پیش از ذخیرهٔ تحقیق در Neo4j، نوع subject،
شناسه و NULL بودن آدرس غیرآدرس‌ها را حفظ می‌کند؛ leg نوع‌دار با جهت نامعتبر
یا ادعای continuity/ownership/allocation رد می‌شود. query ذخیرهٔ Neo4j تغییر
نکرده است. این گام اجرای زندهٔ Neo4j و پذیرش چرخهٔ واقعی VMها را تأیید نمی‌کند.
