# DB-04 — جدول‌ها و viewهای دادهٔ پایه

قرارداد مقصد دادهٔ پایه در نسخهٔ ۳ تکمیل شده است: **۲۹ جدول، ۲۱ view و ۴۰۴ ستون جدول**. تعریف مؤثر همان نسخه در [core-contract-v3.json](core-contract-v3.json) و migration قابل بررسی بیت‌کوین در [SQL نسخهٔ ۳](../../dockerizd_bitcoin/sql/migrations/20261026_0003_core_evidence.sql) قرار دارد. هر چهار schema job همان بستهٔ Rust را مصرف می‌کنند؛ دیتابیس، ClickHouse و volume هر شبکه روی VM خودش مستقل است.

## تغییرهای این گام

| خانواده | تکمیل قرارداد |
|---|---|
| `aml_ingested_blocks` | شمارش ردیف‌های هر خانوادهٔ fact در `expected_counts_json` و شواهد مبدأ در JSON؛ فیلدهای جدید در view canonical هم ارائه می‌شوند |
| `aml_transactions` | قرارداد کامل قبلی، مبلغ UInt256 دقیق و JSON شواهد حفظ شد؛ reader مشترک از canonical می‌خواند |
| `aml_address_relationships` | `event_sub_index`، آرایهٔ مرتب `trace_address`، `token_id` دقیق nullable و JSON شواهد؛ token_id ارائه‌شده باید با شناسهٔ NFT منطبق باشد |
| `aml_transaction_features` | JSON شواهد مبدأ کنار featureهای نسخه‌دار |
| `aml_semantic_aml_events` | ترتیب اصلی و فرعی رویداد، detector و JSON شواهد مبدأ |
| `aml_sync_state` | `source_cursor_json` برای نگهداری cursor مبدأ در تبدیل صریح آینده |
| `aml_ingestion_failures` | tx_hash، retryable و زمان اولین/آخرین شکست و رفع خطا به‌صورت nullable، همراه JSON شواهد |
| `aml_ingestion_benchmarks` | وضعیت اجرا، نوع مبدأ، شروع/پایان، خطا، جزئیات metric و نرخ‌های nullable؛ view جدید `aml_ingestion_benchmarks_current` آخرین revision هر benchmark را می‌خواند |

فیلدهای جدید، دادهٔ قدیمی را با مقدار قطعی ساختگی جایگزین نمی‌کنند: زمان‌ها و retryable نامعلوم `NULL` می‌مانند؛ وضعیت benchmark قدیمی `unknown` است. JSON پیش‌فرض `{}` شواهد بازیابی‌شده از گذشته محسوب نمی‌شود. نبود کلید در شمارش commit یعنی آن خانواده تولید/تأیید نشده است؛ به معنی صفر رویداد نیست.

`shared/warehouse/src/core.rs` برای این هشت خانواده، reader محدود با فیلتر اجباری شبکه و بازهٔ بلاک مناسب ارائه می‌کند. مبالغ UInt256 رشتهٔ دقیق می‌مانند و UInt64 بدون گردشدن خوانده می‌شود. نوشتن batch مشترک، انطباق header و شمارش ردیف‌های هر commit را پیش از fence نهایی کنترل می‌کند؛ همچنان مالک انحصاری cursor لازم است. این کنترل شمارش جایگزین تطبیق کامل محتوای fact نیست؛ writer بیت‌کوین علاوه بر آن تمام ستون‌های ذخیره‌شده را تطبیق می‌دهد.

writer بیت‌کوین اکنون metadata بلاک و شمارش چهار خانوادهٔ fact، شواهد legهای UTXO و زمان‌های چرخهٔ خطا را ثبت می‌کند. `block_hash` از reader مشترک canonical استفاده می‌کند. raw evidence بیت‌کوین در این مسیر metadata و مدل استخراج‌شده است؛ ادعای ذخیرهٔ تمام پاسخ خام RPC نمی‌شود. برای بیت‌کوین trace و NFT نامرتبط‌اند و مقدار انتقال ساختگی آدرس‌به‌آدرس تولید نمی‌شود.

## ارتقا و بازیابی

نسخه‌های ۱ و ۲ و SQL آن‌ها تغییر نکرده‌اند. runner به‌ترتیب ۱، ۲ و ۳ را اعمال می‌کند و ledger هر سه را حفظ می‌کند. نسخهٔ ۳ افزایشی است؛ هیچ جدول، volume یا ردیف قدیمی حذف نمی‌شود. دادهٔ ناسازگار در preflight محدود پیش از ALTER رد می‌شود.

در قطع وسط migration فقط پیشوند ستون‌های اعلام‌شده، constraintهای اعلام‌شده و تعریف دقیق قدیم یا جدید view پذیرفته می‌شود. نوع یا default متفاوت، ستون ناشناس، view تغییریافته یا constraint گمشدهٔ نسخهٔ ثبت‌شده باعث توقف می‌شود؛ اجرای مجدد این drift را تأیید یا پنهان نمی‌کند. `--check` فقط خواندنی باقی می‌ماند.

## محدودهٔ پایان‌یافته و کار باقی‌مانده

این مرحله قرارداد مقصد و دسترسی مشترک دادهٔ پایه است. نصب schema نسخهٔ ۳ روی fixtureهای مستقل چهار شبکه آزمون می‌شود. writer/readerهای legacy سه شبکهٔ TRON، Ethereum و BSC هنوز فعال‌اند؛ انتقال تاریخچه، تبدیل cursorهای آن‌ها، مقایسهٔ خروجی API و تغییر نهایی مسیرها در DB-08 باقی است. بنابراین برابری کل دیتابیس فعال یا پایان P0 ادعا نمی‌شود.

DB-05 مرحلهٔ بعد است: قرارداد خانواده‌های تحلیلی و تخصصی باید پیش از انتقال نهایی تاریخچه کامل شود. ING-04 همچنان جلو نمی‌رود. دامنهٔ تست و نتیجهٔ اجرای واقعی در [DB04_VALIDATION.md](DB04_VALIDATION.md) ثبت می‌شود. فرهنگ دادهٔ DB-01 snapshot تاریخی نسخهٔ ۱ را نگه می‌دارد و هدف نسخهٔ ۳ را جدا معرفی می‌کند.
