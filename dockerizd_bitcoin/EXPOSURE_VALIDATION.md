# Bitcoin AML-03 validation — 2026-10-28

Completed bounded on-demand directional exposure from approved seed evidence,
through canonical Bitcoin outpoints and the existing v5 ClickHouse tables, to
the existing central risk policy and Bitcoin panel. Storage schema stays at
39 tables, 53 views and 682 physical columns. Each network keeps its own database
on its own VM. No migration, new scoring weights or background service was added.

## Executed checks

- **45 ordinary Bitcoin Rust tests** pass with Rust 1.92 and locked dependencies.
  Two new interval tests cover fees, one satoshi, maximum supply, invalid ranges
  and exhaustive feasible integer allocations for small transaction totals.
- **Four ClickHouse integration tests** pass on a fresh disposable
  ClickHouse **23.8.16.16**: two existing pipeline/backfill/restart/UTXO/path/reorg
  regressions, the AML-01 intelligence acceptance and the new exposure acceptance.
  The other ignored resilience suites were not rerun in this step.
- The exposure test writes four amount-preserving synthetic blocks through the
  actual extractor and warehouse writer. These are **not consensus-valid Bitcoin
  blocks**. It checks incoming/outgoing paths, multiple hops, addressless scripts,
  grouped inputs from the same seed address, fees, non-additive summaries and
  exact persisted evidence. A reused address on an unrelated outpoint cannot
  bridge paths. Mixed-input allocation `[0,99]` is context only; a positive
  interval can support the existing policy.
- Approved exchange evidence stops traversal and remains context. Truncated
  results stay unsealed and unscored. Source deactivation, revocation, chain
  source changes and approval at a previously unlabelled dependency invalidate
  the old result. Batched attribution snapshots match single-address reads.
- **22 ordinary central tests and two ignored acceptance tests** pass. The new
  test consumes the actual JSON generated by the ClickHouse exposure acceptance.
  It checks direct, indirect, outgoing and script paths, plus mixed/service/
  unrelated/revoked negatives. Changing bounds, method, seed, outpoint, snapshot,
  network or ownership claims prevents scoring. Duplicated paths add no risk.
- Local HTTP callbacks and a Neo4j query-store mock exercise the actual central
  create, reopen and Export handlers. Changing exposure dependencies makes the
  saved investigation historical and current risk UNKNOWN, while preserving
  historical evidence and assessment. Unavailable run verification is unverified.
  This is **not a live Neo4j or multi-VM deployment**.
- Actual `bitcoin_aml exposure` help, compute and inspect CLI commands pass
  against the disposable database, without a usable RPC URL. Inspect returns
  the same run as current. No `.env` or production credentials were used.
- The in-app browser loads the actual Bitcoin HTML/JS with the central acceptance
  JSON served locally. It displays the 9- and 60-satoshi bounds as `0.00000009`
  and `0.00000060` BTC, the existing 55-point exposure signal, and expandable
  transaction/outpoint details. The historical response keeps both paths but
  displays Historical and UNKNOWN current risk. Screenshots were inspected.
  This local fixture check is not live mainnet browser acceptance.
- **102 Python tests**, data-dictionary regeneration/offline validation,
  four-network Compose rendering (including the opt-in Bitcoin exposure tool),
  Rust formatting and Git whitespace checks pass.

## Reproducing the exposure acceptance

Use a **fresh disposable** ClickHouse with the fixture user `bitcoin_test` and
password `bitcoin-test-only`; the test creates the fixed fixture database
`bitcoin_exposure_test`. Run from the repository root with Rust 1.92:

```bash
BITCOIN_TEST_CLICKHOUSE_URL=http://127.0.0.1:8123 \
BITCOIN_EXPOSURE_ACCEPTANCE=/tmp/bitcoin-exposure.json \
cargo test --locked --manifest-path dockerizd_bitcoin/Cargo.toml \
  --test exposure -- --ignored --nocapture

BITCOIN_EXPOSURE_ACCEPTANCE=/tmp/bitcoin-exposure.json \
cargo test --locked --manifest-path analytical_node/Cargo.toml \
  canonical_bitcoin_exposure_reaches_risk_create_reopen_and_export -- --ignored
```

## Still open

The method is a conservative value-label inference, not identification of
particular satoshis, common ownership or laundering. Per-path intervals can
overlap and must not be summed. Empty results do not establish absence of risk;
the ingested window, hop limit and resource caps apply. BIP30 occurrence guards
are implemented, but this step adds no consensus-valid historical BIP30 fixture.
CoinJoin/change detection, clustering, continuous refresh, replay, shared
policy/signal/assessment persistence (AML-04), four-network legacy cutover,
production capacity and real-node/VM acceptance remain open.

Deploy the updated central consumer before allowing Bitcoin exposure in a live
investigation. No real intelligence source was imported or approved here.
